# IFRS 17 on the platform — design

**Date:** 2026-10-05 · **Branch:** `ifrs17` (from main at a687ef2b) · **Status:** approved in brainstorming, awaiting spec review

**Source document:** *IFRS 17 Chart of Accounts and Posting Guide for a Life Insurance Company* (prepared for Nlolo
Company, September 2026, 47 pages) — "the guide". Section and entry references below (2.4, A-06, P-03, 5.5 …) are
the guide's. Where this spec and the guide differ, this spec states the difference and why.

## 1. Purpose

Make the platform's books IFRS 17 (and IFRS 9 / IFRS 15) compliant in the way the guide prescribes: the platform
posts every real event daily into accounts that sit inside the insurance contract liability, an IFRS 17 engine
measures each group of contracts at period end, and its results post back through a controlled pipeline. Finance
posts everything outside the policy system (equity, investments, tax, payroll, reinsurance statements) through
approved manual journals. Month-end and year-end run as an enforced sequence.

### What the platform has today (finaccounting, 2026-10-05)

- A 36-account placeholder chart (finaccounting V5, V8, V9), every account "pending FINANCE sign-off".
- Hard-coded posting: `PostingRule` (one account pair per event) plus per-module listeners; ~30 event types post.
- Journal lines carry account, direction, amount, currency, period and policy number. `gl_posting.group_id`
  exists but is never filled. `group_of_contracts`, `csm_ledger`, `lrc_ledger`, `lic_ledger` exist (M1) and are
  unused.
- Premium is accrued to 2140 Unearned Premium and never earned; claims are expensed when paid.
- Not posted at all: savings/deposits (accumulation), commission when earned, claim registration, loan interest,
  levies, proposal deposits.
- Reinsurance cession posts the ceded **sum assured** as premium (known M9 bug).
- Product versions carry `ifrs_measurement_model` GMM or PAA only.
- No manual journals, no period close or lock, no reversals, no engine interface, no IFRS 17 reports.

## 2. Decisions (user, 2026-10-05)

| # | Decision |
|---|---|
| D1 | **Engine: external now, built-in later.** The external actuarial engine is integrated now (file exchange + API on one pipeline). A built-in engine for term and PAA products is a later phase plugged into the same pipeline. PAA monthly earning (I-03) is built in from the start. |
| D2 | **Chart: adopt the guide's chart exactly** — codes, names, types, normal balances, modes — and **start the development ledger clean** (journal and posting rows deleted, chart re-seeded). No other data is touched. |
| D3 | **Posting rules: a versioned file in the repository now**, with a read-only console page; a database editor with maker-checker later. |
| D4 | **Channel and branch captured on the case at sale**, defaulted from the agent (or staff member, or scheme), copied to the policy at issue, never changed. Agents and staff get a home branch only as the default. |
| D5 | **IFRS 17 group = portfolio + annual cohort + profitability bucket**: portfolio code on the product; cohort = issue year; bucket set by the actuary per product version. Assigned at issue, never changed. |
| D6 | **Engine interface: console file exchange first**, built as a draft → validate → approve → post pipeline, with a documented API on the same pipeline. |
| D7 | **Accounting defaults (§3) are an effective-dated accounting policy register**, not product configuration: maker-checker, sign-off reference, prospective only, every journal line records the policy version it was posted under. |

## 3. Accounting policy register (baseline elections)

Each row is an **election** with an effective-from date. A new version needs a proposer, a different approver and a
sign-off reference (actuary memo, auditor letter). Elections are never edited; a change is a new dated version and
applies prospectively. A change of accounting policy needing restatement (IAS 8) is made through manual journals
(I4) or engine results (I5) — the system never re-posts history.

**Measurement model per product line (baseline):**

| Product line (portfolio) | Model | Investment component rule |
|---|---|---|
| Term life, single credit life (TERM, CRL single) | GMM | none (return-of-premium benefit: premiums returned) |
| Group life, credit-life schemes, family funeral (GRPL, CRL scheme, FUN) | PAA | none |
| Whole life, endowment, money-back, income (WL, END, MB) | GMM | surrender value at the event date |
| With-profits (PAR) | VFA | surrender value including attached bonuses |
| Unit-linked (ULIP) | VFA | fund value at the event's price |
| Savings accounts, fixed-term deposits (SAV, DEP) | IFRS 9 | the whole balance (not insurance) |
| Immediate annuity (IANN) | GMM | none, unless a guaranteed period |
| Deferred annuity / pension (DANN, PEN) | IFRS 9 in deferral; a **new** GMM contract at vesting (G-08) | — |

**Other baseline elections:**

| Election | Baseline |
|---|---|
| Policy loans | inside the insurance contract liability (2125–2127); interest is a contract inflow, LN_INT |
| Acquisition cash flows | GMM/VFA: in the LRC (2123), recognised over time; PAA: expensed when incurred (5310, para 59(a)) |
| OCI option (para 88(b)) | off — discount-rate effects to profit or loss (7120) |
| Riders | in the host contract's group |
| Premium billing | accrual: invoice generated → Dr 2122 / Cr 2121 (PAA: 2142/2141) |
| Contract recognition | issue date; money before issue in 2410 |
| Cohort | annual (calendar year of issue) |

**Flags for the actuary and auditors** (configurable, never hard-wired): SAV/DEP are IFRS 9 only while the death
benefit is the balance alone — a version paying more on death is GMM; pre-vesting pensions are IFRS 9 only while
annuity rates are not guaranteed — a guaranteed-rate version is GMM from inception.

**Overrides:** a product version may carry a measurement-model override only where the register allows overrides
for that product line, and only to a model the register lists as permitted.

## 4. Architecture

Six sub-projects, each its own plan, branch, gate and merge to main, in this order (I4 may overlap I2/I3):

```
I1 Ledger foundation ──┬── I2 Classification at sale ── I3 Posting engine ──┐
                       ├── I4 Manual journals ──────────────────────────────┼── I6 Reports & close
                       └──────────────────────────── I5 Engine interface ───┘   (needs I3, I4, I5)
                                                     (needs I1, I3)
Later: built-in engine (term, PAA) behind the I5 pipeline.
```

All of it lives in `finaccounting`, except: I2's fields on product, underwriting, policy, distribution and iam;
new events in the emitting modules (I3); refdata lists (branches, channels).

Out of scope: tax computation, payroll, the fund manager's and custodian's systems, instrument-level investment
holdings — their figures arrive as manual journals (N-01 … N-14, O-01 … O-11).

## 5. I1 — Ledger foundation

### 5.1 Chart of accounts
- All accounts of guide 2.5, codes exact, with name, type (asset, liability, contra-liability, contra-asset, equity,
  contra-equity, income, expense, contra-expense, clearing, memo), normal balance, **mode** (AUTO, MAN, BOTH), group
  heading, and the "used for" note.
- Account codes are constants in one Java class; a test asserts the seeded chart equals the guide list (as
  `ChartOfAccountMigrationV5Test` does today).
- `PostingRule.accountTypeFor` (leading digit) is replaced: type and normal balance are explicit per account (the
  guide has contra accounts and clearing accounts the leading-digit rule cannot express).

### 5.2 Journal header and lines
- **Header:** source type (EVENT, MANUAL, ENGINE_RUN, SYSTEM), source event + source ref with the existing
  once-only unique index, period, posted-at, posted-by, preparer, approver, reason, reason code, document refs,
  reverses-journal id, auto-reverse-on date, accounting policy version, rule version (events), engine run id.
- **Line:** account, direction, amount, currency, IFRS 17 group, measurement model, movement type (2.4), product,
  portfolio, channel, branch, fund, reference type + reference (policy, claim, agent, reinsurer, treaty).

### 5.3 Database-enforced rules
- Every journal balances (a deferred constraint trigger: Σ Dr = Σ Cr per journal at commit).
- Posted journals and lines are never updated or deleted (triggers refuse UPDATE/DELETE).
- An account's mode decides which journal sources may post to it (guide 2.3: AUTO = "posted only by the insurance
  system from events, or by the IFRS 17 engine upload"):

  | Mode | EVENT | SYSTEM | ENGINE_RUN | MANUAL |
  |---|---|---|---|---|
  | AUTO | yes | yes | yes | **no** |
  | MAN | no | no | yes | yes |
  | BOTH | yes | yes | yes | yes, with a reason code |

  SYSTEM covers the platform's own scheduled runs: PAA earning (I-03), auto-reversals, the year-end closing run
  (M-07 posts to AUTO account 3310). The expense allocation P-19 (which debits AUTO account 2123) is posted as an
  ENGINE_RUN-type allocation run through the I5 pipeline, not as a manual journal.
- A line in a LOCKED period is refused; in CLOSING only sources allowed by the month-end step are accepted.
- 9xxx accounts must net to zero for a period to move from CLOSING to LOCKED (checked by the close action).

### 5.4 Periods
OPEN → CLOSING → LOCKED. Reopening LOCKED → OPEN needs a proposer and a different approver with a reason.
Corrections are reversal journals dated in the current open period.

### 5.5 Accounting policy register
The register of §3: elections, versions, effective dates, proposer, approver, sign-off reference, and a read
endpoint answering "the election in force for X on date D". Every journal records the version.

### 5.6 Clean start
A migration deletes all `journal_entry` and `gl_posting` rows and drops the old 36-account chart for every tenant,
then seeds the guide's chart. The opening-balance mechanism (O-11 via 9190) is available for real go-live
balances. The M1 tables `csm_ledger`, `lrc_ledger`, `lic_ledger` are dropped (replaced by I5's engine results);
`group_of_contracts` is redesigned in I2.

## 6. I2 — Classification at sale

- **Product:** `portfolio_code`, mandatory for new products, from a controlled list (TERM, WL, END, MB, PAR, ULIP,
  SAV, DEP, IANN, DANN, PEN, GRPL, CRL, FUN).
- **Version:** `expected_profitability_bucket` (ONEROUS / NO_SIGNIFICANT_RISK / REMAINING, default REMAINING),
  part of what the actuary signs off at publish; optional measurement-model override within the register (§3).
- **Reference data:** branches (DSM, ARU, MWZ, DOD, ZNZ, maintained list) and channels (AGENT, BROKER,
  BANCASSURANCE, DIRECT, DIGITAL).
- **People:** agents get a channel and home branch; staff get a home branch.
- **Case:** captures channel and branch; defaults from the agent (agent case), the staff member (staff case) or the
  scheme (group / credit-life scheme); editable until issue.
- **Issue:** resolves the measurement model (register in force on the issue date, or the allowed override), builds
  the group key portfolio + issue year + bucket (e.g. `END-2026-PROF`), finds or creates the tenant's group, and
  stamps group, model, channel and branch on the policy. Database triggers refuse later changes. Riders join the
  host's group; a vesting pension creates a new contract in a new cohort (G-08).
- **Event:** `policy.PolicyIssued` carries the classification; finaccounting keeps its own policy-classification
  copy from it (§7.2).
- **Development backfill (one-off, recorded as such):** portfolio from product category; channel AGENT where an
  agent of record exists, else DIRECT; branch DSM; bucket REMAINING; cohort = issue year.

## 7. I3 — Posting engine

### 7.1 Rules file
`finaccounting/posting-rules.yaml`, versioned with the code. Each rule: `event`, `model` (GMM/VFA/PAA/IFRS9/ANY),
optional `when` (conditions on payload fields), `lines` (Dr/Cr, account, amount source field), `movementType`
(literal or from a payload field), `effectiveFrom`/`effectiveTo`. Startup validation refuses to start the
application on an unbalanced rule, an unknown account, an account in MAN mode, or two rules matching the same
event × model × condition × date. A read-only console page lists the rules.

### 7.2 Dimensions
Finaccounting keeps `policy_classification` (group, model, product, portfolio, channel, branch, fund where
relevant), filled from `policy.PolicyIssued` — posting never calls another module. Non-policy events (agent,
reinsurer, treaty) carry their own reference.

### 7.3 Investment-component split
The emitting module computes the split and sends it on the event (claims: surrender value at the date of death;
unit-linked: fund value; payouts: the investment-component share). The rule names the payload field. Finaccounting
never computes a split.

### 7.4 Coverage of the guide's daily entries

| Area | Guide entries | Change |
|---|---|---|
| Proposal money, declines, free-look | A-01, A-02, A-03, A-17, A-18 | new events where missing |
| Billing | A-06, A-07/A-08, A-10/A-11, A-12, A-13, A-14, J-01 | re-mapped; PAA → 2141/2142 |
| Commission | A-04, A-09, A-05, A-15, A-20/A-21 | **new** "commission earned" event; paid with WHT 2610 |
| Levies | A-19 | **new**, rate from configuration |
| Claims | B-01, B-02, B-03, B-04, B-05, B-06, C-04, I-05, J-02 | **new** LIC at registration; IC split |
| Maturities, surrenders, paid-up | C-01, C-02, C-03, C-05, C-06, C-07 | re-mapped to 2124/2212/2213 |
| Survival and income benefits | D-01 … D-05 | re-mapped |
| Policy loans | E-01 … E-06 | **new** monthly interest E-02 (closes the documented gap) |
| Unit-linked (VFA) | F-01 … F-09 | 2150 → 2131 per fund; charges → 2132; revaluation mirrored 7235/7130 |
| Savings, deposits, pension accumulation (IFRS 9) | G-01 … G-08 | **new** — accumulation posts nothing today |
| Annuities | H-01, H-02, H-03 | re-mapped; WHT → 2615 |
| Waiver of premium | J-03 | when a waiver benefit exists |
| Reinsurance | K-01, K-02, K-03, B-05 | **rebuilt** on the bordereau; fixes the cession bug |

### 7.5 PAA earning (I-03)
A monthly built-in job earns, for each PAA policy, the cover elapsed in the month from 2141 to 4160, keyed per
policy × month so a re-run earns nothing twice.

### 7.6 Unmapped events
An event with no matching rule is recorded in an **unmapped-events queue** on the finance console, never dropped.
A non-empty queue blocks the month-end close.

## 8. I4 — Manual journals

- Any balanced journal on MAN or BOTH accounts (AUTO refused in the database and on screen, per the mode table in
  §5.3). Section M's year-end entries M-07/M-11 run as the SYSTEM closing run of §10, not here. Template from
  sections M, N, O, Q, R pre-fills lines; free-form allowed.
- Each carries a reason (and a reason code on BOTH accounts, guide 2.3), at least one attached document, and its
  dimensions where they apply (fund, reinsurer/treaty, branch).
- DRAFT → SUBMITTED → APPROVED (posted in the open period) or REJECTED (with reason). Approver ≠ preparer and holds
  the finance-approver role.
- Correction by a one-click reversal journal (needs approval), dated in the current open period.
- Auto-reversing journals (accruals, P-18) carry a reverse-on date; the platform posts the reversal on the first day
  of the next period without a second approval.
- Recurring templates (depreciation, lease interest) may be saved; each month's journal is still approved.
- Console: Finance → Journals (draft, submit, approve, reject, reverse, attach), templates library, filters.

## 9. I5 — Engine interface

### 9.1 Extract (out)
After month-end steps 1–5 (refused while the unmapped queue is non-empty): one row per group × movement type ×
account × direction for the period; a policy-level detail file per group (policy, group, model, issue date, sum
assured, premium, frequency, status, VFA fund value, investment-component balances); opening and closing balances
of every 21xx/22xx account by group. CSV and Excel; each extract stored with its run number.

### 9.2 Results (in)
One row per group × account × Dr/Cr × amount × movement type (P-01 … P-17), plus the engine's closing LRC, LIC and
CSM per group, all tagged with the engine run id.

**Validation (all-or-nothing, every error listed):** every group exists and was extracted; every account is in the
engine-results set (21xx measurement, 4xxx, 5xxx engine lines, 6xxx, 7xxx IFIE, 14xx reinsurance, 1510/2190
reclass, and for an expense-allocation run 5210, 5215, 2123, 5310, 1620 against 8490); balanced per
group and in total; the period is CLOSING; the run id is new.

### 9.3 Pipeline
UPLOADED → VALIDATED | REJECTED → APPROVED (second person, actuary sign-off reference) → POSTED through 9160, which
must end at zero. The ledger's insurance contract liability per group is reconciled to the engine's closing
balances; a difference blocks the period lock unless finance records an explained tolerance. A replacement run
reverses the previous run's journals in full and posts the new one; both are kept.

### 9.4 API
`POST /ifrs17/engine-runs` and the extract downloads, on the same pipeline, documented in OpenAPI. The later
built-in engine plugs in here.

## 10. I6 — Reports and close

- **Management reports (5.6)** from movement-type tags: gross written premium, penalty and fee income, commission,
  claims paid (claim vs investment component), reinsurance cost; filters by period, product, portfolio, channel,
  branch, group; export.
- **IFRS 17 P&L** (4xxx − 5xxx ± 6xxx ± 7xxx − 8xxx) and the **movement reconciliation per group** (paras 100–105),
  from engine-run journals tagged by movement.
- **Month-end checklist (5.5):** the eight steps per period, in order; system-checkable steps verified
  automatically (unmapped queue empty, 9xxx at zero, engine reconciled).
- **Presentation reclass (P-18)** auto-reversing.
- **Year-end close (5.7):** an approved closing run: classes 4–8 → 3310 → 3210, with dividends (M-07, M-11) and
  statutory reserve (M-08); OCI reserves stay in equity.
- **Policy register report:** every account, rule and election the guide marks "confirm with auditors", in one
  document for the actuary and auditors before go-live.

## 11. Error handling

- Rule load failures stop startup with the offending rule named.
- Posting failures are counted (`lifeplatform_finaccounting_event_processing_failed_total`, existing) and the event
  lands in the unmapped/failed queue with the error; finance retries from the console once fixed.
- Engine-run validation reports every error at once; nothing posts until a clean run is approved.
- Database guards (balance, immutability, mode, period) raise named constraint errors surfaced as 409/422 with the
  guard's words.

## 12. Testing

- Every rule against its guide example with the guide's amounts as fixtures (A-01 … K-03).
- Policy → journal lifecycle per product line, asserting the guide's entries in order.
- Database guards: unbalanced, update, delete, AUTO/MAN mode, locked period.
- Engine pipeline: each validation error, approval by the same person refused, replacement run, 9160 at zero,
  reconciliation difference blocking the lock.
- Month-end checklist ordering; year-end close.
- e2e: a manual journal through two people; an engine-run upload, approval and reconciliation; a period close.

## 13. Delivery

I1 → I2 → I3 → I5 → I6, with I4 after I1 (in parallel with I2/I3 if useful). Each sub-project gets its own plan
(writing-plans), branch from main, affected-class test runs, full e2e at its gate, review, merge `--no-ff` and push.
The phase-2 built-in engine is specified separately when I5 has merged.
