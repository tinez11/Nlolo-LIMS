# M6 — Claims Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the `claims` module end-to-end — intake, adjudication with separation of duties, the sealed `ClaimDetails` hierarchy, MinIO evidence linkage, and asynchronous settlement through `payment`'s request/confirm loop — and close the policy-lifecycle hole so a settled death or maturity claim actually terminates the policy.

**Architecture:** `claims` is a new Spring Modulith module depending on `policy::api`, `underwriting::api`, `party::api`, `document::api`, `refdata::api`. It is **purely event-driven with `payment`** (`docs/02-module-architecture.md:14`, A3): it publishes `claims.ClaimSettlementRequested` and consumes `payment.DisbursementCompleted`/`DisbursementFailed`, never calling `payment` synchronously. `payment::api` must NOT be added to its allowed dependencies. Settlement is therefore asynchronous — the settlement-decision endpoint returns 202, not a final result.

**Tech Stack:** Java 21, Spring Boot 3.3.5, Spring Modulith, Postgres 16 (schema-per-module + RLS), MinIO (via `document`), Testcontainers, WireMock (via `payment`'s existing gateway stub), Micrometer/Prometheus.

- **Cross-module references are opaque columns, never FKs** (`docs/06-database-schema.md:29`). `claims.claim.policy_number` and `claimant_party_id` have no foreign keys; existence is validated through the owning module's API at write time.
- **Money columns need `CHECK (... > 0)`** and money in events is always the nested shape `{"amount": "<plain decimal string>", "currencyCode": "<3 upper-case letters>"}`.
- **An `AFTER_COMMIT` `@TransactionalEventListener` MUST use a `PROPAGATION_REQUIRES_NEW` `TransactionTemplate`**, never a plain `@Transactional` call. A plain `@Transactional` (REQUIRED) call from an `AFTER_COMMIT` callback silently joins the already-committed producer transaction and never commits. `src/main/java/tz/co/nlolo/lifeplatform/policyloan/application/PaymentEventListener.java` (102 lines) is the exact template; copy its shape.
- **A consumer of `payment.DisbursementCompleted`/`DisbursementFailed` MUST filter on `purpose`** — several modules ride the same event type. Claims filters `"CLAIM_SETTLEMENT"`.
- **`Idempotency-Key` for settlement is required and must be non-blank.** `BillingApiImpl.java:101-104` documents why: a blank key forwarded to `payment` is rejected by `PaymentRequestListener.requireKey` *inside an AFTER_COMMIT listener*, where the exception is swallowed and logged — i.e. it looks like a successful request that reached the rail zero times. Reject blank at the claims boundary with a 400.
- **`refdata` lookup pattern:** `referenceDataApi.getValue("TZ_CONTESTABILITY_MONTHS", "TZ")` returns a raw `String` the caller parses. Precedent: `UnderwritingApiImpl.java:167`, `PolicyApiImpl.java:411`. Current seeded value is `'24'` (a documented PLACEHOLDER pending open item C3 — the value is a data change, not a code change).
- **No new `refdata` migration.** M6 adds no reference parameters; `TZ_CONTESTABILITY_MONTHS` already exists.
- **`schemaVersion` is always `1`** (hardcoded in `DomainEventEnvelope.of`). Event payloads are `Map<String, Object>` with zero compile-time coupling — field names are strings, so they must be declared in `api/asyncapi-events.yaml` and match the producer exactly.

## Pre-adjudicated decisions (user-approved before authoring — do not re-litigate)

1. **A settled DEATH/MATURITY claim terminates the policy.** Add minimal `policy` transitions (`markMatured`, `terminateForSettledClaim`) publishing `policy.PolicyMatured`/`policy.PolicySurrendered`. Without this, `billing` keeps generating premium invoices against a deceased policyholder's policy forever. The full 6-event surrender/maturity choreography stays deferred.
2. **Contestability reaches claims by exposing `underwritingCaseId` on `PolicyView`.** This realizes the already-documented claims→underwriting sync lookup (`docs/01-domain-map.md:127`) with one canonical implementation. **Verified fact: `PolicyApi.issuePolicy(UUID underwritingCaseId, ...)` currently accepts that parameter and discards it entirely** — no column, no field, not in the published event. So this needs a new `policy` migration and a nullable column, and every policy issued before M6 will have it NULL, unbackfillably.
3. **The 422 coverage-consistency check is scoped to DEATH and MATURITY.** `PolicyApiImpl.java:95-99` only ever creates a DEATH coverage row (because `ProductApi` exposes no benefit-schedule getter), so a DISABILITY/CRITICAL_ILLNESS coverage check could never pass. Skip it for those two types with an explicit code comment rather than shipping a check that silently proves nothing. Fixing it properly needs `product` work, deferred.
4. **`CLAIM_EVIDENCE` gets its own MinIO bucket** (`claim-evidence`), matching the existing per-evidence-type pattern (`kyc-evidence`, `underwriting-evidence`). Requires one switch arm in `MinioDocumentStorage` and one line in `infra/docker-compose.yml`.

## Design decisions made by this plan (flag for final review)

- **The claim status state machine is defined here for the first time.** No doc defines it — grepping `UNDER_ASSESSMENT`/`SETTLEMENT_REQUESTED`/`REOPENED` across `docs/` returns zero hits, yet "Claims state machine tested per claim type" is M6 acceptance criteria. The legal transitions are exactly:
  ```
  REGISTERED           -> UNDER_ASSESSMENT      (first assessment submitted)
  REGISTERED           -> APPROVED              (MATURITY only, auto-approval, no assessment)
  UNDER_ASSESSMENT     -> APPROVED | REJECTED   (settlement decision by CLAIMS_MANAGER)
  APPROVED             -> SETTLEMENT_REQUESTED  (ClaimSettlementRequested published)
  SETTLEMENT_REQUESTED -> SETTLED               (payment.DisbursementCompleted, purpose=CLAIM_SETTLEMENT)
  SETTLEMENT_REQUESTED -> APPROVED              (payment.DisbursementFailed -- retryable, see below)
  REJECTED             -> REOPENED              (CLAIMS_MANAGER reopen, e.g. new evidence)
  SETTLED              -> REOPENED              (CLAIMS_MANAGER reopen, e.g. dispute)
  REOPENED             -> UNDER_ASSESSMENT      (new assessment submitted)
  ```
  `REOPENED` is given a real producer deliberately: the CHECK constraint and the OpenAPI enum both already contain it, and M5's final review established that an enum value no code path can reach is a real smell (`PolicyStatus.MATURED` sat unreachable for three milestones).
- **`DisbursementFailed` returns the claim to `APPROVED`, not to a new failure state.** The CHECK constraint offers no `SETTLEMENT_FAILED` value, and `docs/02-module-architecture.md:125` says a failure means the claim "is flagged to a staff retry worklist rather than silently retried". `APPROVED` + a persisted `settlement_failure_reason` + an alertable counter gives exactly that: the decision still stands, the payout is retryable by staff, and the reason is preserved.
- **`IN_DOUBT` produces no event at all, by design** (`api/asyncapi-events.yaml:571-592` records this explicitly and warns future readers not to "complete" the file by inventing a `payment.DisbursementInDoubt` event). So an indeterminate rail outcome leaves the claim resting at `SETTLEMENT_REQUESTED` with no claims-side signal. This is **not** fixable from claims; `payment` already alerts on it via `lifeplatform_payment_in_doubt_total`. Document it in the listener's javadoc so the next reader doesn't mistake it for a missed case.
- **`ClaimDetails` subtype field sets are invented here.** Both `docs/04-api-contracts.md:84` and `openapi-claims.yaml:126` deferred them to "Deliverable 6", which then only stored `details JSONB NOT NULL`. The field sets below are a judgment call pending real claim-form requirements — flag for sign-off, not silent acceptance.
- **`payeeRef` is supplied at settlement-decision time, not registration.** For a DEATH claim the payee is a beneficiary, not the claimant, so the manager determines it when approving. Follows `billing`'s precedent of an explicit caller-supplied `payerRef` (`PartyView` exposes no phone/MSISDN, so it cannot be derived).
- **`policy.BeneficiaryChanged` consumption is deliberately NOT built.** `api/asyncapi-events.yaml:75` lists claims as a consumer ("refresh any open claim's beneficiary snapshot"), but `docs/02-module-architecture.md:125` — the authoritative module contract — lists only the payment pair. Claims stores no beneficiary snapshot to refresh (it reads beneficiaries live from `PolicyApi.getPolicy` at settlement time), so there is nothing for the handler to do. Deliberate omission, stated so it isn't read as an oversight.

```sql
-- db-migrations/claims/V2__grants_rls_money_checks_evidence_and_settlement_columns.sql
-- Completes claims/V1, which shipped with zero GRANTs and RLS on 1 of its 3 tables -- the exact
-- bug class billing/V2:1-3 documents for billing/V1, and that M1/M2/M3 each fixed for every
-- other schema. Migrations run as the Postgres superuser (scripts/migrate.sh), which owns the
-- schema, so this gap was invisible to any test whose DataSource connected as that same
-- superuser. app_role is the app's real runtime identity and had no access whatsoever.

-- =============================================================================
-- 1. GRANTs. Without these the module is unreachable at runtime.
-- =============================================================================
GRANT USAGE ON SCHEMA claims TO app_role;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA claims TO app_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA claims GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_role;

-- =============================================================================
-- 2. RLS completion. V1 covered claims.claim only; both child tables carry
--    tenant_id NOT NULL and had no policy at all, so app_role could read every
--    tenant's assessments and settlement decisions.
-- =============================================================================
ALTER TABLE claims.claim_assessment ENABLE ROW LEVEL SECURITY;
CREATE POLICY claim_assessment_tenant_isolation ON claims.claim_assessment
    USING (tenant_id = current_setting('app.current_tenant_id', true)::uuid);

ALTER TABLE claims.settlement_decision ENABLE ROW LEVEL SECURITY;
CREATE POLICY settlement_decision_tenant_isolation ON claims.settlement_decision
    USING (tenant_id = current_setting('app.current_tenant_id', true)::uuid);

-- =============================================================================
-- 3. Money guards. Every other module got these (policy/V2, policyloan/V3,
--    billing/V2:38-41); claims/V1 has none. A non-positive approved amount is a
--    data-entry error, never a legitimate settlement.
-- =============================================================================
ALTER TABLE claims.claim
    ADD CONSTRAINT claim_approved_amount_positive
    CHECK (approved_amount IS NULL OR approved_amount > 0);

ALTER TABLE claims.claim_assessment
    ADD CONSTRAINT claim_assessment_recommended_amount_positive
    CHECK (recommended_amount IS NULL OR recommended_amount > 0);

ALTER TABLE claims.settlement_decision
    ADD CONSTRAINT settlement_decision_approved_amount_positive
    CHECK (approved_amount IS NULL OR approved_amount > 0);

-- =============================================================================
-- 4. Evidence linkage. claims/V1 has NO table linking a claim to the document
--    refs that evidence it, despite "document evidence upload/retrieval tested
--    against MinIO" being M6 acceptance criteria. document_ref is an opaque
--    string returned by DocumentApi.upload -- no FK, per docs/06:29.
-- =============================================================================
CREATE TABLE claims.claim_evidence (
    claim_evidence_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id         UUID NOT NULL,
    claim_id          UUID NOT NULL REFERENCES claims.claim(claim_id),
    document_ref      VARCHAR(100) NOT NULL,   -- opaque ref into document, never an FK
    description       VARCHAR(500),
    uploaded_by       VARCHAR(100) NOT NULL,
    uploaded_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT claim_evidence_unique_ref_per_claim UNIQUE (claim_id, document_ref)
);
CREATE INDEX idx_claim_evidence_claim ON claims.claim_evidence (claim_id);
CREATE INDEX idx_claim_evidence_tenant ON claims.claim_evidence (tenant_id);

ALTER TABLE claims.claim_evidence ENABLE ROW LEVEL SECURITY;
CREATE POLICY claim_evidence_tenant_isolation ON claims.claim_evidence
    USING (tenant_id = current_setting('app.current_tenant_id', true)::uuid);

GRANT SELECT, INSERT, UPDATE, DELETE ON claims.claim_evidence TO app_role;

-- =============================================================================
-- 5. Settlement columns.
--    payee_ref: the mobile-money destination, supplied by the CLAIMS_MANAGER at
--      decision time (for a DEATH claim the payee is a beneficiary, not the
--      claimant, and PartyView exposes no MSISDN, so it cannot be derived).
--    settlement_idempotency_key: the client-supplied key forwarded to payment.
--      Persisted so a retry after DisbursementFailed can deliberately use a NEW
--      key while the original remains auditable.
--    settlement_failure_reason: on payment.DisbursementFailed the claim returns
--      to APPROVED (retryable) and this preserves why -- the "staff retry
--      worklist" of docs/02:125.
-- =============================================================================
ALTER TABLE claims.settlement_decision ADD COLUMN payee_ref VARCHAR(100);
ALTER TABLE claims.claim ADD COLUMN settlement_idempotency_key VARCHAR(100);
ALTER TABLE claims.claim ADD COLUMN settlement_failure_reason VARCHAR(500);

-- Idempotency keys are tenant-scoped, matching payment/V2's registry fix (a
-- global-unique key would let one tenant's key collide with another's).
CREATE UNIQUE INDEX idx_claim_settlement_key
    ON claims.claim (tenant_id, settlement_idempotency_key)
    WHERE settlement_idempotency_key IS NOT NULL;
```

```java
    /** First assessment submitted. REGISTERED or REOPENED -> UNDER_ASSESSMENT. */
    public void beginAssessment() {
        if (status == ClaimStatus.UNDER_ASSESSMENT) {
            return;
        }
        if (status != ClaimStatus.REGISTERED && status != ClaimStatus.REOPENED) {
            throw new InvalidClaimStateException(
                "Claim " + claimId + " is " + status + ", cannot begin assessment");
        }
        this.status = ClaimStatus.UNDER_ASSESSMENT;
    }

    /** Settlement decision approved. UNDER_ASSESSMENT -> APPROVED, or REGISTERED -> APPROVED for
     * MATURITY only (auto-approval, docs/03-aggregate-design.md:134 / Cl3). */
    public void approve(BigDecimal approvedAmount, String approvedCurrency) {
        if (status == ClaimStatus.APPROVED) {
            return;
        }
        boolean maturityAutoApproval = claimType == ClaimType.MATURITY && status == ClaimStatus.REGISTERED;
        if (status != ClaimStatus.UNDER_ASSESSMENT && !maturityAutoApproval) {
            throw new InvalidClaimStateException(
                "Claim " + claimId + " is " + status + ", cannot approve");
        }
        if (approvedAmount == null || approvedAmount.signum() <= 0) {
            throw new ClaimValidationException("Approved amount must be positive");
        }
        this.status = ClaimStatus.APPROVED;
        this.approvedAmount = approvedAmount;
        this.approvedCurrency = approvedCurrency;
    }

    /** Settlement decision rejected. UNDER_ASSESSMENT -> REJECTED. Note MATURITY has no
     * auto-rejection counterpart: auto-approval is the only automatic transition. */
    public void reject() {
        if (status == ClaimStatus.REJECTED) {
            return;
        }
        if (status != ClaimStatus.UNDER_ASSESSMENT) {
            throw new InvalidClaimStateException(
                "Claim " + claimId + " is " + status + ", cannot reject");
        }
        this.status = ClaimStatus.REJECTED;
    }

    /** ClaimSettlementRequested published. APPROVED -> SETTLEMENT_REQUESTED. */
    public void markSettlementRequested(String idempotencyKey) {
        if (status == ClaimStatus.SETTLEMENT_REQUESTED) {
            return;
        }
        if (status != ClaimStatus.APPROVED) {
            throw new InvalidClaimStateException(
                "Claim " + claimId + " is " + status + ", cannot request settlement");
        }
        if (idempotencyKey == null || idempotencyKey.isBlank()) {
            throw new ClaimValidationException("A settlement idempotency key is required");
        }
        this.status = ClaimStatus.SETTLEMENT_REQUESTED;
        this.settlementIdempotencyKey = idempotencyKey;
        this.settlementFailureReason = null; // a fresh attempt clears the previous failure
    }

    /** payment.DisbursementCompleted. SETTLEMENT_REQUESTED -> SETTLED. Terminal unless reopened. */
    public void markSettled() {
        if (status == ClaimStatus.SETTLED) {
            return;
        }
        if (status != ClaimStatus.SETTLEMENT_REQUESTED) {
            throw new InvalidClaimStateException(
                "Claim " + claimId + " is " + status + ", cannot mark settled");
        }
        this.status = ClaimStatus.SETTLED;
    }

    /** payment.DisbursementFailed. SETTLEMENT_REQUESTED -> APPROVED, preserving the reason so the
     * claim lands on a staff retry worklist (docs/02-module-architecture.md:125) rather than being
     * silently retried. The decision itself still stands, so APPROVED is the correct resting
     * state, and the CHECK constraint offers no SETTLEMENT_FAILED value. */
    public void markSettlementFailed(String reason) {
        if (status != ClaimStatus.SETTLEMENT_REQUESTED) {
            return; // a redelivered failure after a manual retry already moved it on
        }
        this.status = ClaimStatus.APPROVED;
        this.settlementFailureReason = reason;
    }

    /** CLAIMS_MANAGER reopen. REJECTED or SETTLED -> REOPENED (new evidence, or a dispute).
     * Deliberately does NOT clear approvedAmount: the prior decision stays on the record, and a
     * new decision overwrites it only when one is actually made. */
    public void reopen() {
        if (status == ClaimStatus.REOPENED) {
            return;
        }
        if (status != ClaimStatus.REJECTED && status != ClaimStatus.SETTLED) {
            throw new InvalidClaimStateException(
                "Claim " + claimId + " is " + status + ", only a REJECTED or SETTLED claim can be reopened");
        }
        this.status = ClaimStatus.REOPENED;
    }
```

     * True when the claim falls inside the contestability window and therefore needs a
     * non-disclosure review before approval.
     *
     * <p>Fails CLOSED in two distinct ways, both deliberate:
     * <ul>
     *   <li>A policy issued before M6 has a NULL underwritingCaseId (policy/V4 added the column

## Self-Review Notes

**Judgment calls flagged for the final review — each a place where this plan chose a side:**

1. **The claim status state machine is invented here.** No doc defines it; the roadmap nonetheless makes it acceptance criteria. Most consequential sub-choice: `DisbursementFailed` returns the claim to `APPROVED` rather than a new terminal state, because the CHECK constraint offers no `SETTLEMENT_FAILED` and the decision genuinely still stands.
2. **`REOPENED` is given a real producer** (a `CLAIMS_MANAGER` reopen endpoint) rather than left unreachable. Defensible either way; M5's review established that unreachable enum values are a real smell, but this is scope the roadmap did not ask for.
3. **`ClaimDetails` field sets are invented**, after two documents deferred them to a third that did not define them. Stored as JSONB precisely so a later correction needs no migration.
4. **`SURRENDERED` is reused for a claim-settled policy**, because `policy.policy`'s CHECK offers no `CLAIM_SETTLED` value and widening an existing CHECK to add one is a bigger change than reusing the status whose operative meaning ("coverage discharged, no further premium due") already matches. A reviewer may reasonably argue for a distinct value.
5. **Contestability fails closed on a NULL `underwritingCaseId`**, which every pre-M6 policy will have. This means every claim against an existing policy is flagged for manual review. Correct but operationally heavy — worth confirming with the business.
6. **The 422 coverage check is enforced for DEATH only** (user-approved), so DISABILITY/CRITICAL_ILLNESS claims can be registered against policies that never carried those benefits. The alternative needed `product` work.
7. **`policy.BeneficiaryChanged` is deliberately not consumed**, contradicting `api/asyncapi-events.yaml:75` but matching `docs/02-module-architecture.md:125`. Claims keeps no beneficiary snapshot to refresh.
8. **Separation of duties is enforced on the persisted assessor identity**, not only on the role claim — stricter than the docs literally require.
9. **A settled claim closes the policy from claims' listener**, making `claims` a driver of `policy` lifecycle. An alternative design has `policy` consume `claims.ClaimSettled` itself, inverting the dependency. This plan calls `PolicyApi` directly because `policy::api` is already an allowed claims dependency and the call is synchronous and idempotent; a reviewer may prefer the event-driven inversion.
