# M4 — Billing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the `billing` module (Premium Billing & Collection) — schedule generation from `policy` issuance/endorsement/suspension, invoice generation ahead of due dates, arrears/dunning escalation feeding a `PolicyLapseRecommended` recommendation back to `policy`, and offline field-receipt capture with SLA-based reconciliation-overdue detection — plus the additive fixes to `policy`/`refdata` this module genuinely cannot function without.

**Architecture:** `billing` depends on `policy::api`, `product::api`, `refdata::api` (already declared in `billing/package-info.java`). It has no synchronous callers of its own in this milestone — `payment` (M5) will later request money via `billing.PaymentRequested`, and `omnichannel` (post-M4) will later call `billing`'s read endpoints, but neither exists yet. `billing` reacts to `policy`'s domain events (`PolicyIssued`, `PolicyEndorsed`, `PolicySuspended`, and a new `PolicyResumed` this plan adds) via `@TransactionalEventListener(phase = AFTER_COMMIT)`, mirroring `policy.application.UnderwritingDecisionEventListener`'s established `REQUIRES_NEW` + `TenantContext` save/restore pattern exactly. `billing` publishes `PolicyLapseRecommended`, consumed by a new listener inside `policy` that finally gives `PolicyApi.lapsePolicy` — built and tested since M3, called by nothing — its first real caller.

Two genuinely new pieces of infrastructure, both flagged as judgment calls in Self-Review Notes: (1) `policy` does not store a premium amount, frequency, or anywhere compute one — this plan adds premium fields to `policy` itself (accepted at manual issuance, computed via a new `refdata` placeholder rate for automatic issuance), matching the "additive fix to an already-merged module" precedent M3 established for `product`/`underwriting`. (2) The 24-hour offline-receipt SLA and the arrears/dunning escalation both need a *reliable, timely* state transition with no natural per-request trigger (unlike M3's loan-reservation TTL, which self-heals on the next `reserveLoanValue` call) — this plan splits the concern: a new `pg_cron`-driven, `SECURITY DEFINER` SQL function does the actual state transitions cross-tenant on a 15-minute cadence (the same class of DB-owner-level RLS bypass M3's `policyloan/V2` partition-mirroring trigger already established and passed final review for), while the Java side publishes the resulting domain events opportunistically per-tenant on the next real `BillingApi` call — RLS-safe, self-healing, and honest about which half is guaranteed-on-time and which half is eventually-consistent.

**Tech Stack:** Same as M1–M3 — Spring Boot 3 / Spring Modulith, Spring Data JPA + Hibernate 6, PostgreSQL 16 with RLS + `pg_partman` + `pg_cron`, Flyway-shaped hand-written SQL migrations (Flyway itself disabled — `scripts/migrate.sh` applies files directly), Testcontainers + JUnit 5, `swagger-request-validator-mockmvc` for contract tests.

- **No money `CHECK` constraints exist anywhere in `billing`'s schema.** Following the precedent `db-migrations/policy/V2__endorsement_append_only_and_money_checks.sql` and `db-migrations/policyloan/V3__money_check_constraints.sql` set (a negative/zero amount was a real, fixed Critical in M3 — `policyloan`'s `MoneyDto` accepted a signed amount that inverted into a cash-value inflation exploit), Task 1's V2 migration adds `CHECK (premium_amount > 0)` / `CHECK (amount > 0)` to `billing.billing_schedule`, `billing.premium_invoice`, and `billing.field_receipt`.
- **`policy` does not expose premium amount, premium frequency, or any renewal/maturity date — genuinely nowhere in the codebase.** `PolicyApi.IssueRequest` already has a `premiumFrequency` field, but `PolicyApiImpl.issuePolicy` never reads it, and there is no `premium_amount` column anywhere in `db-migrations/policy/`. Task 1 closes this additively, matching M3's precedent for `ProductSnapshotView`/`UnderwritingCaseView`: a **new** migration `db-migrations/policy/V3__premium_fields.sql` adds `premium_amount NUMERIC(19,2) NOT NULL`, `premium_currency CHAR(3) NOT NULL DEFAULT 'TZS'`, `premium_frequency VARCHAR(10) NOT NULL CHECK (premium_frequency IN ('MONTHLY','QUARTERLY','ANNUALLY'))` to `policy.policy`; `Policy.java`, `PolicyApi.IssueRequest`, `PolicyView`, `ManualIssueRequestDto`, `PolicyResponseDto`, and `openapi-policy.yaml`'s `PolicyView`/`ManualIssueRequest` schemas all gain the three fields additively — no existing caller of any of these breaks, since the new components are appended, not inserted.
- **A policy's premium amount is established at issuance, not computed by `billing` — `billing`'s entire job is scheduling against an already-known amount, matching the domain map's own framing** ("this context decides what is owed, by when… it never touches a payment rail directly" — a schedule generator, not a rating engine). Two issuance paths need it differently:
  - **Manual issuance** (`POST /policies/manual-issue`, staff-only): staff supplies the agreed premium directly, exactly like they already supply `sumAssured`. `ManualIssueRequestDto` gains a required `@NotNull @Valid MoneyDto premiumAmount`.
  - **Automatic issuance** (`UnderwritingDecisionEventListener`, system-triggered, no human premium input): no actuarial rating engine exists anywhere in the codebase (M2's `SimpleRulesEngine` is a deliberate placeholder; Drools is deferred). Following the exact externalization pattern already used four times (`TZ_CONTESTABILITY_MONTHS`, `TZ_REINSTATEMENT_WINDOW_MONTHS`, `TZ_SUSPENSION_TO_LAPSE_MONTHS`, `TZ_POLICY_LOAN_ANNUAL_INTEREST_RATE`), this plan adds a **new** `refdata` placeholder, `TZ_BASE_PREMIUM_RATE_PER_MILLE` (annual premium per thousand of sum assured, seeded `'5.0'`, `-- PLACEHOLDER, pending Actuarial sign-off`), and computes `annualPremium = sumAssuredAmount * (baseRatePerMille / 1000) * (1 + loadingPercent / 100)`, then divides by 12/4/1 for MONTHLY/QUARTERLY/ANNUALLY to get the per-instalment `premiumAmount`. **Flagged as a judgment call** — see Self-Review Notes.
- **`refdata`'s `V1` and `V2` are already taken.** A new placeholder seed is `db-migrations/refdata/V3__seed_billing_parameters.sql`, following the exact comment-then-`INSERT`-then-`-- PLACEHOLDER` convention `V2` established. This file also seeds the dunning-escalation day thresholds (below).
- **Dunning escalation timing is unspecified anywhere in the design docs** (`docs/03-aggregate-design.md` names the 5 levels and their actions but never says how many days separate them). This plan externalizes it to `refdata` rather than hardcoding it, using the existing `getCodes(String codeSetKey)` method (already used for `POLICY_SUSPENSION_ELIGIBLE_CATEGORIES`): a new code set `DUNNING_ESCALATION_DAYS` with codes `LEVEL_2`/`LEVEL_3`/`LEVEL_4`/`LEVEL_5`, values `'7'`/`'14'`/`'21'`/`'30'` (days since the invoice became `OVERDUE`), each `-- PLACEHOLDER, pending Collections/Actuarial sign-off`. Level 1 begins the moment an `ArrearsCase` opens (no threshold needed).
- **`policy.resumeSuspendedPolicy` currently publishes no event at all** — its own code comment states this explicitly ("No dedicated 'PolicyResumed' event exists in the event catalog… billing's M4 consumption is out of scope regardless"). M4 is exactly the milestone that needs it: `billing` must resume schedule generation when a suspension lifts. Task 1 adds one `eventPublisher.publishEvent(DomainEventEnvelope.of("policy.PolicyResumed", ...))` call to the existing, already-tested `resumeSuspendedPolicy` method — additive, same class of proactive fix as M3's addition of `underwriting.UnderwritingDecisionMade`. **Flagged as a judgment call** — modifying an already-merged module outside a "proactive fix" the plan explicitly calls for; see Self-Review Notes.
- **`PolicyApi.lapsePolicy` exists, is fully tested, and has never had a real caller** (M3's ledger recorded this explicitly). This plan gives it one: `billing` publishes `PolicyLapseRecommended` when an `ArrearsCase` reaches dunning level 5; a new `policy.application.PolicyLapseRecommendedEventListener` consumes it and calls the existing `policyApi.lapsePolicy(...)`, mirroring `UnderwritingDecisionEventListener`'s exact mechanics (`AFTER_COMMIT`, `REQUIRES_NEW` `TransactionTemplate`, `TenantContext` save/set/restore, catch-log-no-dead-letter). Per the event catalog's own framing ("billing recommends, policy alone performs the lapse transition"), this listener does not re-derive eligibility — it trusts the recommendation and calls `lapsePolicy` directly, since `Policy.lapse()`'s own domain guard (ACTIVE or SUSPENDED only) is the authoritative check either way.
- **No `@Scheduled`/cron mechanism exists anywhere in application code, and the M3 precedent explains why a naive one would be wrong here too.** `ModuleArchitectureB1`'s TTL sweep runs opportunistically per-call because a cross-tenant background thread with no `TenantContext` sees zero rows on every RLS-protected table, and there is no tenant-directory table to iterate, and `app_role` must never have `BYPASSRLS` (CI hard-fails on it). Unlike the loan-reservation TTL, though, **there is no natural per-request trigger for "this receipt has gone quiet" or "this policyholder hasn't paid"** — nothing calls billing just because time has passed. This plan therefore does NOT reuse the per-call-sweep pattern verbatim; it splits the concern:
  - **State transitions run on a real timer, cross-tenant, via `pg_cron`** calling a new `billing.sweep_billing_state()` `SECURITY DEFINER` SQL function (owned by the migration-applying role, so it bypasses RLS by virtue of table ownership — the same class of DB-internal, non-`app_role` privilege M3's `policyloan/V2__partition_tenant_controls.sql` event trigger already established and passed final review for; **not** a new exception to "`app_role` never bypasses RLS," since `app_role` is never involved). This function flips `DUE`/`IN_GRACE` invoices past their grace period to `OVERDUE`, opens/escalates `ArrearsCase`s per the `DUNNING_ESCALATION_DAYS` thresholds, flips `PENDING_RECONCILIATION` field receipts past the `OFFLINE_RECEIPT_SLA_HOURS` window to `RECONCILIATION_OVERDUE`, and refreshes a small, deliberately non-tenant-scoped metrics table (`billing.overdue_metrics_snapshot`, single row, no RLS — same class of decision as `refdata.reference_code_set` being deliberately not tenant-scoped) that a Micrometer gauge reads for the `lifeplatform_field_receipt_overdue_count` alert metric. Scheduled via `SELECT cron.schedule('billing-sweep', '*/15 * * * *', $$CALL billing.sweep_billing_state()$$);` in a **new** post-migration file, `db-migrations/_post-migration/configure-billing-sweep.sql`, run by the same CD pipeline step that already runs `configure-pg-partman.sql` — **never** as a Flyway-style migration itself.
  - **Domain-event publication runs opportunistically, per-tenant, RLS-safe, on the next real `BillingApi` call** — a Java-side sweep that queries (within the caller's own `TenantContext`) for `ArrearsCase`s whose `dunningLevel` has advanced past `lastNotifiedDunningLevel` and `FieldReceipt`s that are `RECONCILIATION_OVERDUE` with `notifiedOverdueAt IS NULL`, publishes the corresponding domain event for each, and stamps the notification marker. This is the same "self-healing on next real access, not a fixed wall-clock timer" framing `ModuleArchitectureB1`'s TTL sweep used — but here it is honest that only the *notification* is eventually-consistent; the underlying *business state* (is this invoice actually overdue, is this receipt actually unreconciled) is guaranteed correct within 15 minutes regardless of any tenant traffic, by the `pg_cron` half. **Flagged as a judgment call** — see Self-Review Notes.
- **`Idempotency-Key` is accepted, not enforced** — same deliberate scope cut as every prior milestone (`clientIdempotencyKey` on field-receipt capture is checked for uniqueness at the DB layer via the composite unique index above, which is real deduplication of the *receipt itself*, but the HTTP `Idempotency-Key` header convention other endpoints accept-but-ignore is unrelated and stays unenforced pending M5).
- **`payment` does not exist until M5.** `billing.PaymentRequested` is published with no consumer (matching `policyloan.LoanDisbursementRequested`'s precedent from M3); `billing`'s listener for `payment.PaymentConfirmed`/`PaymentFailed` is **not built in this plan** — field receipts and invoices can reach `PENDING_RECONCILIATION`/`OVERDUE` but never automatically reach `RECONCILED`/`PAID` via a real payment event in M4. Staff can still `waiveInvoice` manually. Stated explicitly, not silently dropped.
- **Value types stay raw, matching every other module.** `BillingApi` methods take `String policyNumber`, `UUID` ids, and `BigDecimal amount, String currency` pairs — never a `Money`/`PolicyNumber` wrapper type, matching `PolicyApi`/`PolicyLoanApi`'s established convention.
- **Money JSON is a decimal string, matching `openapi-common.yaml#/components/schemas/Money`** (`^-?\d+(\.\d{1,2})?$` for the shared schema; every module narrows it to `@DecimalMin("0.01")` at its own request-binding `MoneyDto`, per M3's final-review finding I3 — `billing`'s own `MoneyDto` must carry `@DecimalMin("0.01")` from the start, not as a later fix).
- **Event payloads follow the `party`/`policy`/`policyloan` precedent**: constructor-inject `ApplicationEventPublisher`, publish inside `@Transactional` methods via `eventPublisher.publishEvent(DomainEventEnvelope.of("billing.<EventType>", tenantId, payload))`, payload as `Map<String, Object>` — `Map.of(...)` where every value is non-null, a mutable `LinkedHashMap` wherever a field is genuinely nullable (none of `billing`'s payloads have a nullable field in this plan, so `Map.of(...)` throughout is correct and simpler).
- **Module-specific `@RestControllerAdvice` classes MUST carry `@Order(Ordered.HIGHEST_PRECEDENCE)`.** The root `GlobalExceptionHandler` is `@Order(Ordered.LOWEST_PRECEDENCE)`; `@ExceptionHandler` resolution across advice beans is first-matching-bean-wins, not merged-by-specificity — this exact regression has been caught twice already on this project. `BillingExceptionHandler` maps only `billing`-owned exception types.
- **Controllers derive audit fields from `@AuthenticationPrincipal Jwt jwt` → `jwt.getSubject()`**, never a hardcoded string. Request DTOs carry Bean Validation matching each OpenAPI schema's `required` list, with `@Valid` on every `@RequestBody`.
- **Service methods read tenant via `TenantContext.get()` per-call**, never cached/injected as a field or constructor parameter. Every mutating method is `@Transactional`.
- **Contract tests validate against `api/openapi/openapi-billing.yaml` via `swagger-request-validator-mockmvc`**, following `PolicyContractTest`/`PolicyLoanContractTest`'s idiom exactly (`@Testcontainers` + `@AutoConfigureMockMvc` + `SecurityMockMvcRequestPostProcessors.jwt()` + `OpenApiValidationMatchers.openApi().isValid(SPEC_PATH)`). **Every test must be falsifiable** — no asserting against empty result sets; this codebase has a documented recurring vacuous-test problem (three in M2's final review, at least four more instances caught and fixed across M3's task and final reviews). Any test that seeds DB state via raw SQL (a cash-value bump, a premium-amount seed) MUST assert the seed's `executeUpdate()` return value before trusting the state it set up — M3's final review found this exact gap in three separate files.
- **`api/openapi/openapi-billing.yaml`'s existing four operations and one schema are a genuine, usable draft, but incomplete**: no `securitySchemes` block locally (this is a pre-existing, already-accepted platform-wide habit — all ten module specs reference `customersAuth`/`agentsAuth`/`staffAuth` by name and rely on `openapi-common.yaml`'s definitions being resolvable by the validator's bundling; it produces a benign per-request WARN log line, already observed and accepted in M3, not a hard failure); no `additionalProperties: false` on `InvoiceView`; no `400`/`401`/`404`/`409`/`422` responses declared on most operations. Task 6 closes every gap the actual implementation needs (a wrong/missing declared status is a hard contract-test failure, per M3's own finding on this exact class of gap) and adds the operations this plan's `BillingApi` surface needs beyond the four already sketched: listing/regenerating a billing schedule is intentionally **not** given its own endpoint (schedule regeneration is entirely event-driven off `PolicyEndorsed`/`PolicySuspended`/`PolicyResumed`, with no manual trigger needed for M4's scope) — the four existing operations plus nothing new cover 100% of this plan's public HTTP surface.
- **Out of scope for M4, stated explicitly, not silently dropped:**
  - Real actuarial premium calculation (rating tables, mortality tables, health loadings beyond underwriting's existing flat loading percent) — the `TZ_BASE_PREMIUM_RATE_PER_MILLE` placeholder above is a deliberate simplification, not a rating engine.
  - `payment.PaymentConfirmed`/`PaymentFailed` consumption — `payment` is M5; invoices/receipts reach `OVERDUE`/`RECONCILIATION_OVERDUE` but never automatically reach `PAID`/`RECONCILED` in this plan.
  - Multi-currency premium schedules — every amount in this plan flows through in whatever currency `sumAssuredCurrency` was issued in (`TZS` in every real scenario today, matching every prior milestone's stated scope).
  - `distribution`'s agent-hierarchy validation of `agentId` on field-receipt capture — `agentId` is accepted as an opaque `UUID` (matching the migration comment "opaque ref into distribution"), not validated against a real agent registry, since `distribution` (M7) does not exist yet.
  - A dedicated `communication` module consuming `GracePeriodTriggered`/`PremiumOverdue`/`FieldReceiptReconciliationOverdue` for actual SMS/staff-worklist delivery — `communication` does not exist yet (no milestone builds it standalone per the roadmap; it is meant to be wired incrementally per-milestone). This plan publishes the events correctly and durably (picked up by `audit`'s existing generic listener, proving the events are real and observable) but builds no SMS/worklist consumer.

```sql
-- db-migrations/policy/V3__premium_fields.sql
-- Deliverable 8 / M4 (billing): policy never stored a premium amount, frequency, or currency
-- anywhere -- premiumFrequency was accepted on PolicyApi.IssueRequest since M3 but silently
-- dropped by PolicyApiImpl.issuePolicy, and no premium_amount column existed at all. billing's

    ADD COLUMN premium_amount NUMERIC(19,2) NOT NULL DEFAULT 0,
    ADD COLUMN premium_currency CHAR(3) NOT NULL DEFAULT 'TZS',
    ADD COLUMN premium_frequency VARCHAR(10) NOT NULL DEFAULT 'MONTHLY'
        CHECK (premium_frequency IN ('MONTHLY', 'QUARTERLY', 'ANNUALLY'));

-- The DEFAULTs above exist ONLY to satisfy the NOT NULL constraint against any pre-existing
-- row (there are none in a fresh environment, but ALTER TABLE ADD COLUMN NOT NULL without a
-- default fails outright against a populated table) -- every future INSERT (i.e. every
-- issuePolicy call from this commit forward) supplies real values explicitly; the defaults
-- are never relied upon by application code.
ALTER TABLE policy.policy ALTER COLUMN premium_amount DROP DEFAULT;
ALTER TABLE policy.policy ALTER COLUMN premium_frequency DROP DEFAULT;

ALTER TABLE policy.policy ADD CONSTRAINT chk_premium_amount_positive CHECK (premium_amount > 0);
```

```java
import tz.co.nlolo.lifeplatform.DomainEventEnvelope;
import tz.co.nlolo.lifeplatform.TenantContext;

import tz.co.nlolo.lifeplatform.product.api.ProductApi;

import org.springframework.context.ApplicationEventPublisher;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.math.BigDecimal;
import java.time.LocalDate;
import java.time.Period;
import java.util.List;
import java.util.Map;
import java.util.UUID;

@Service
public class BillingApiImpl implements BillingApi {

    // Schedule generation pre-creates invoices this far ahead of need, mirroring the platform's
    // established convention of pre-creating partitions/reservations ahead of when they're
    // required rather than generating them lazily at due-date time (docs/06's partition-headroom
    // rationale; Module-Architecture-B1's TTL-sweep self-healing framing). 12 months covers a
    // full ANNUALLY cycle and 12x/4x a MONTHLY/QUARTERLY one.
    private static final int SCHEDULE_HORIZON_MONTHS = 12;

    private final BillingScheduleRepository billingScheduleRepository;
    private final PremiumInvoiceRepository premiumInvoiceRepository;
    private final ArrearsCaseRepository arrearsCaseRepository;
    private final FieldReceiptRepository fieldReceiptRepository;
    private final ProductApi productApi;
    private final ApplicationEventPublisher eventPublisher;

    public BillingApiImpl(BillingScheduleRepository billingScheduleRepository, PremiumInvoiceRepository premiumInvoiceRepository,
                           ArrearsCaseRepository arrearsCaseRepository, FieldReceiptRepository fieldReceiptRepository,
                           ProductApi productApi, ApplicationEventPublisher eventPublisher) {
        this.billingScheduleRepository = billingScheduleRepository;
        this.premiumInvoiceRepository = premiumInvoiceRepository;
        this.arrearsCaseRepository = arrearsCaseRepository;
        this.fieldReceiptRepository = fieldReceiptRepository;
        this.productApi = productApi;
        this.eventPublisher = eventPublisher;
    }

    @Override
    public InvoiceView getNextDueInvoice(String policyNumber) {
        UUID tenantId = TenantContext.get();
        return premiumInvoiceRepository.findFirstByPolicyNumberAndTenantIdAndStatusInOrderByDueDateAsc(
                policyNumber, tenantId, List.of("DUE", "IN_GRACE"))
            .map(this::toView)
            .orElseThrow(() -> new InvoiceNotFoundException(null));
        // NOTE: InvoiceNotFoundException(null) is a placeholder call shape -- see Step 1's
        // exception class. Add a second constructor InvoiceNotFoundException(String message)
        // taking a literal message (e.g. "No invoice currently due for policy " + policyNumber)
        // for this specific 404-with-no-id case, since the UUID-based constructor doesn't fit
        // here. Update Step 1's class accordingly before this compiles.
    }

    @Override
    public List<InvoiceView> listInvoices(String policyNumber, InvoiceStatus status) {
        UUID tenantId = TenantContext.get();
        List<PremiumInvoice> invoices = status == null
            ? premiumInvoiceRepository.findByPolicyNumberAndTenantIdOrderByDueDate(policyNumber, tenantId)
            : premiumInvoiceRepository.findByPolicyNumberAndTenantIdAndStatusIn(policyNumber, tenantId, List.of(status.name()));
        return invoices.stream().map(this::toView).toList();
    }

    @Override
    @Transactional
    public InvoiceView waiveInvoice(UUID invoiceId, String reason, String waivedBy) {
        UUID tenantId = TenantContext.get();
        PremiumInvoice invoice = premiumInvoiceRepository.findByInvoiceIdAndTenantId(invoiceId, tenantId)
            .orElseThrow(() -> new InvoiceNotFoundException(invoiceId));
        invoice.waive(reason);
        premiumInvoiceRepository.save(invoice);
        arrearsCaseRepository.findByInvoiceIdAndTenantIdAndResolvedAtIsNull(invoiceId, tenantId)
            .ifPresent(ArrearsCase::resolve);
        eventPublisher.publishEvent(DomainEventEnvelope.of("billing.InvoiceWaived", tenantId,
            Map.of("invoiceId", invoiceId, "policyNumber", invoice.getPolicyNumber(), "reason", reason, "waivedBy", waivedBy)));
        return toView(invoice);
    }

    // ---- PolicyEventListener entry points (package-private -- called only from this module's
    // own event listener, never from the REST layer or another module) ----

    @Transactional
    void generateScheduleForNewPolicy(UUID tenantId, String policyNumber, UUID productVersionId,
                                       LocalDate issueDate, BigDecimal premiumAmount, String premiumCurrency, String premiumFrequency) {
        LocalDate firstDueDate = nextPeriodStart(issueDate, premiumFrequency);
        BillingSchedule schedule = new BillingSchedule(tenantId, policyNumber, premiumFrequency, premiumAmount, premiumCurrency, firstDueDate);
        billingScheduleRepository.save(schedule);
        generateInvoicesAhead(tenantId, schedule, productVersionId, issueDate);

    @Transactional
    void regenerateScheduleForEndorsement(UUID tenantId, String policyNumber, UUID productVersionId, LocalDate effectiveDate) {
        // Per db-migrations/billing/V1's own column comment: never mutated in place -- the old
        // ACTIVE schedule is TERMINATED and a new one created ACTIVE, so schedule history is a
        // sequence of rows, not edits. This mirrors policyloan's own append-only-ledger posture.
        billingScheduleRepository.findByPolicyNumberAndTenantIdAndStatus(policyNumber, tenantId, "ACTIVE")
            .ifPresent(old -> {
                old.terminate();

            });

        // (no endorsement type in policy.PolicyApi.EndorsementInput carries either field as of
        // M3) -- this method exists so a future endorsement type CAN regenerate the schedule
        // without billing needing further changes, but for M4 the only real caller
        // (PolicyEventListener.onPolicyEndorsed) is a documented no-op scope limitation; see
        // Self-Review Notes. Left as a real, callable method rather than dead code because the
        // event listener structure needs a symmetric handler regardless.
    }

    @Transactional
    void pauseScheduleForSuspension(UUID tenantId, String policyNumber) {
        billingScheduleRepository.findByPolicyNumberAndTenantIdAndStatus(policyNumber, tenantId, "ACTIVE")
            .ifPresent(schedule -> {
                schedule.suspend();
                billingScheduleRepository.save(schedule);
            });
    }

    void resumeScheduleAfterSuspension(UUID tenantId, String policyNumber, UUID productVersionId) {
        billingScheduleRepository.findByPolicyNumberAndTenantIdAndStatus(policyNumber, tenantId, "SUSPENDED")

                // Reusing the ACTIVE-status setter is wrong here -- there is no "unsuspend"
                // domain verb on BillingSchedule (only suspend()/terminate() exist, matching
                // the migration's 3-value CHECK). Add a package-private `reactivate()` method
                // to BillingSchedule (Task 2's file) that sets status back to "ACTIVE" -- do
                // this now, in this task, rather than leaving Task 2 incomplete in hindsight.
                schedule.reactivate();
                billingScheduleRepository.save(schedule);
                generateInvoicesAhead(tenantId, schedule, productVersionId, schedule.getNextDueDate());
            });
    }

    private void generateInvoicesAhead(UUID tenantId, BillingSchedule schedule, UUID productVersionId, LocalDate fromDate) {
        ProductSnapshotView snapshot = productApi.getSnapshotByVersionId(productVersionId);
        LocalDate cursor = schedule.getNextDueDate();
        LocalDate horizon = fromDate.plusMonths(SCHEDULE_HORIZON_MONTHS);
        List<PremiumInvoice> toCreate = new java.util.ArrayList<>();
        while (!cursor.isAfter(horizon)) {
            LocalDate graceEnd = cursor.plusDays(snapshot.gracePeriodDays());
            toCreate.add(new PremiumInvoice(tenantId, schedule.getBillingScheduleId(), schedule.getPolicyNumber(),
                cursor, schedule.getPremiumAmount(), schedule.getPremiumCurrency(), graceEnd));
            cursor = nextPeriodStart(cursor, schedule.getPremiumFrequency());
        }
        premiumInvoiceRepository.saveAll(toCreate);
        schedule.advanceNextDueDate(cursor);
        billingScheduleRepository.save(schedule);
        for (PremiumInvoice invoice : toCreate) {
            eventPublisher.publishEvent(DomainEventEnvelope.of("billing.PremiumInvoiceGenerated", tenantId,
                Map.of("invoiceId", invoice.getInvoiceId(), "policyNumber", invoice.getPolicyNumber(), "dueDate", invoice.getDueDate().toString(),
                       "amount", Map.of("amount", invoice.getAmount().toPlainString(), "currencyCode", invoice.getCurrency()))));
        }
    }

    private LocalDate nextPeriodStart(LocalDate from, String frequency) {
        Period step = switch (frequency) {
            case "MONTHLY" -> Period.ofMonths(1);
            case "QUARTERLY" -> Period.ofMonths(3);
            case "ANNUALLY" -> Period.ofYears(1);
            default -> throw new IllegalArgumentException("Unknown premium frequency: " + frequency);
        };
        return from.plus(step);
    }

    private InvoiceView toView(PremiumInvoice invoice) {
        Integer dunningLevel = arrearsCaseRepository.findByInvoiceIdAndTenantIdAndResolvedAtIsNull(invoice.getInvoiceId(), invoice.getTenantId())
            .map(ArrearsCase::getDunningLevel).orElse(null);
        return new InvoiceView(invoice.getInvoiceId(), invoice.getPolicyNumber(), invoice.getDueDate(),
            invoice.getAmount(), invoice.getCurrency(), InvoiceStatus.valueOf(invoice.getStatus()),
            invoice.getGracePeriodEndsAt(), dunningLevel);
    }
}
```

```java
    private final TransactionTemplate requiresNewTransactionTemplate;

    public PolicyEventListener(BillingApiImpl billingApiImpl, PlatformTransactionManager transactionManager) {
        this.billingApiImpl = billingApiImpl;
        this.requiresNewTransactionTemplate = new TransactionTemplate(transactionManager);
        this.requiresNewTransactionTemplate.setPropagationBehavior(TransactionTemplate.PROPAGATION_REQUIRES_NEW);

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onDomainEvent(DomainEventEnvelope<?> envelope) {
        switch (envelope.eventType()) {
            case "policy.PolicyIssued" -> withTenant(envelope, this::handlePolicyIssued);
            case "policy.PolicyEndorsed" -> withTenant(envelope, this::handlePolicyEndorsed);
            case "policy.PolicySuspended" -> withTenant(envelope, this::handlePolicySuspended);
            case "policy.PolicyResumed" -> withTenant(envelope, this::handlePolicyResumed);

            @SuppressWarnings("unchecked")
            Map<String, Object> payload = (Map<String, Object>) envelope.payload();
            requiresNewTransactionTemplate.executeWithoutResult(status -> handler.accept(payload));
        } catch (Exception e) {
            log.error("billing failed to process {} for tenant {}", envelope.eventType(), envelope.tenantId(), e);
        } finally {
            if (previousTenant != null) {
                TenantContext.set(previousTenant);
            } else {
                TenantContext.clear();
            }
        }
```

```java
 * same as UnderwritingDecisionEventListener's own no-dead-letter posture.

@Component
public class PolicyLapseRecommendedEventListener {

    private static final Logger log = LoggerFactory.getLogger(PolicyLapseRecommendedEventListener.class);

    private final PolicyApi policyApi;
    private final TransactionTemplate requiresNewTransactionTemplate;

    public PolicyLapseRecommendedEventListener(PolicyApi policyApi, PlatformTransactionManager transactionManager) {
        this.policyApi = policyApi;
        this.requiresNewTransactionTemplate = new TransactionTemplate(transactionManager);
        this.requiresNewTransactionTemplate.setPropagationBehavior(TransactionTemplate.PROPAGATION_REQUIRES_NEW);
    }

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onDomainEvent(DomainEventEnvelope<?> envelope) {
        if (!"billing.PolicyLapseRecommended".equals(envelope.eventType())) {
            return;
        }
        @SuppressWarnings("unchecked")
        Map<String, Object> payload = (Map<String, Object>) envelope.payload();
        String policyNumber = (String) payload.get("policyNumber");
        UUID previousTenant = TenantContext.getOrNull();
        TenantContext.set(envelope.tenantId());
        try {
            requiresNewTransactionTemplate.executeWithoutResult(status ->
                policyApi.lapsePolicy(policyNumber, "system:billing-lapse-recommendation"));
        } catch (Exception e) {
            log.error("Automatic lapse failed for policy {} following billing's recommendation", policyNumber, e);
        } finally {
            if (previousTenant != null) {
                TenantContext.set(previousTenant);
            } else {
                TenantContext.clear();
            }
        }
    }
}
```

```sql
-- db-migrations/_post-migration/configure-billing-sweep.sql
-- Run by the CD pipeline immediately after Flyway migrations complete, same convention as
-- configure-pg-partman.sql (never as a Flyway migration itself). SECURITY DEFINER means this
-- function executes with the PRIVILEGES OF THE ROLE THAT OWNS IT (the migration-applying role,
-- which owns every table in this schema), bypassing RLS by virtue of table ownership -- the
-- exact same class of DB-internal, non-app_role privilege db-migrations/policyloan/
-- V2__partition_tenant_controls.sql's ddl_command_end event trigger already established and
-- passed M3's final review for. app_role itself is never granted EXECUTE on this function and
-- never bypasses RLS at any point -- this is infrastructure automation, not a request-path
-- privilege escalation. See this plan's Global Constraints for the full reasoning and the
-- honest split this design makes between guaranteed-on-time state (this function) and
-- eventually-consistent notification (BillingApiImpl.publishPendingNotifications, Task 4).
CREATE OR REPLACE FUNCTION billing.sweep_billing_state() RETURNS void
LANGUAGE plpgsql SECURITY DEFINER AS $$
DECLARE
    v_overdue_receipt_count INTEGER;
BEGIN
    -- 1. Invoices whose grace period has fully expired move to OVERDUE.
    UPDATE billing.premium_invoice
       SET status = 'OVERDUE'
     WHERE status IN ('DUE', 'IN_GRACE')
       AND grace_period_ends_at IS NOT NULL
       AND grace_period_ends_at < CURRENT_DATE;

    -- 2. Invoices past due_date but still within their grace window move to IN_GRACE (from DUE).
    UPDATE billing.premium_invoice
       SET status = 'IN_GRACE'
     WHERE status = 'DUE'
       AND due_date < CURRENT_DATE
       AND (grace_period_ends_at IS NULL OR grace_period_ends_at >= CURRENT_DATE);

    -- 3. Open an ArrearsCase (dunning level 1) for every newly-OVERDUE invoice without one.
    INSERT INTO billing.arrears_case (tenant_id, invoice_id, policy_number, dunning_level, opened_at)
    SELECT pi.tenant_id, pi.invoice_id, pi.policy_number, 1, now()
      FROM billing.premium_invoice pi
     WHERE pi.status = 'OVERDUE'
       AND NOT EXISTS (
           SELECT 1 FROM billing.arrears_case ac
            WHERE ac.invoice_id = pi.invoice_id AND ac.resolved_at IS NULL
       );

    -- 4. Escalate dunning level on every open ArrearsCase per the refdata-configured thresholds.
    -- Level only ever increases here -- BillingApiImpl.publishPendingNotifications (Task 4) is
    -- what compares against last_notified_dunning_level and never runs backwards either.
    UPDATE billing.arrears_case ac
       SET dunning_level = sub.new_level
      FROM (
          SELECT ac2.arrears_case_id,
                 CASE
                     WHEN now() - ac2.opened_at >= (
                         (SELECT value FROM refdata.reference_code_set WHERE code_set_key = 'DUNNING_ESCALATION_DAYS' AND code = 'LEVEL_5') || ' days')::interval THEN 5
                     WHEN now() - ac2.opened_at >= (
                         (SELECT value FROM refdata.reference_code_set WHERE code_set_key = 'DUNNING_ESCALATION_DAYS' AND code = 'LEVEL_4') || ' days')::interval THEN 4
                     WHEN now() - ac2.opened_at >= (
                         (SELECT value FROM refdata.reference_code_set WHERE code_set_key = 'DUNNING_ESCALATION_DAYS' AND code = 'LEVEL_3') || ' days')::interval THEN 3
                     WHEN now() - ac2.opened_at >= (
                         (SELECT value FROM refdata.reference_code_set WHERE code_set_key = 'DUNNING_ESCALATION_DAYS' AND code = 'LEVEL_2') || ' days')::interval THEN 2
                     ELSE 1
                 END AS new_level
            FROM billing.arrears_case ac2
           WHERE ac2.resolved_at IS NULL
      ) sub
     WHERE ac.arrears_case_id = sub.arrears_case_id
       AND sub.new_level > ac.dunning_level;

    -- 5. Field receipts unmatched by a PaymentConfirmed (which never arrives in M4 -- payment
    -- is M5) within the refdata-configured SLA move to RECONCILIATION_OVERDUE.
    UPDATE billing.field_receipt
       SET status = 'RECONCILIATION_OVERDUE'
     WHERE status = 'PENDING_RECONCILIATION'
       AND captured_at_server < now() - (
           (SELECT value FROM refdata.reference_code_set WHERE code_set_key = 'OFFLINE_RECEIPT_SLA_HOURS' AND code = 'DEFAULT') || ' hours')::interval;

    -- 6. Refresh the global, non-tenant-scoped metrics snapshot the Micrometer gauge reads.
    SELECT count(*) INTO v_overdue_receipt_count FROM billing.field_receipt WHERE status = 'RECONCILIATION_OVERDUE';
    UPDATE billing.overdue_metrics_snapshot SET field_receipt_overdue_count = v_overdue_receipt_count, computed_at = now() WHERE id = 1;
END;
$$;

-- Every 15 minutes -- tighter than pg_partman's daily maintenance cadence, since a 24-hour SLA
-- needs sub-hour granularity to be meaningfully enforced, and the alert rule's own `for: 10m`
-- window implies the underlying metric is expected to move on a similar timescale.
SELECT cron.schedule('billing-sweep', '*/15 * * * *', $$CALL billing.sweep_billing_state()$$);
```

```java
import tz.co.nlolo.lifeplatform.billing.api.BillingApi;
import tz.co.nlolo.lifeplatform.billing.api.InvoiceStatus;
import tz.co.nlolo.lifeplatform.billing.api.InvoiceView;

import jakarta.validation.Valid;
import org.springframework.http.ResponseEntity;
import org.springframework.security.access.AccessDeniedException;
import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.GrantedAuthority;
import org.springframework.security.core.annotation.AuthenticationPrincipal;
import org.springframework.security.oauth2.jwt.Jwt;
import org.springframework.web.bind.annotation.*;

import java.util.List;
import java.util.UUID;

@RestController
public class BillingController {

    private final BillingApi billingApi;
    private final PolicyApi policyApi;

    public BillingController(BillingApi billingApi, PolicyApi policyApi) {
        this.billingApi = billingApi;
        this.policyApi = policyApi;
    }

    @GetMapping("/policies/{policyNumber}/invoices")
    @PreAuthorize("hasRole('REALM_CUSTOMERS') or hasRole('REALM_AGENTS') or hasRole('REALM_STAFF')")
    public ResponseEntity<List<InvoiceResponseDto>> listInvoices(@PathVariable String policyNumber,
                                                                  @RequestParam(required = false) InvoiceStatus status,
                                                                  @AuthenticationPrincipal Jwt jwt, Authentication authentication) {
        PolicyView policy = policyApi.getPolicy(policyNumber);
        enforceCustomerOwnPolicyOnly(policy, jwt, authentication);
        List<InvoiceResponseDto> invoices = billingApi.listInvoices(policyNumber, status).stream().map(InvoiceResponseDto::from).toList();
        return ResponseEntity.ok(invoices);
    }

    @GetMapping("/policies/{policyNumber}/invoices/next-due")
    @PreAuthorize("hasRole('REALM_CUSTOMERS') or hasRole('REALM_AGENTS')")
    public ResponseEntity<InvoiceResponseDto> getNextDueInvoice(@PathVariable String policyNumber,
                                                                 @AuthenticationPrincipal Jwt jwt, Authentication authentication) {
        PolicyView policy = policyApi.getPolicy(policyNumber);
        enforceCustomerOwnPolicyOnly(policy, jwt, authentication);
        InvoiceView invoice = billingApi.getNextDueInvoice(policyNumber);
        return ResponseEntity.ok(InvoiceResponseDto.from(invoice));
    }

    @PostMapping("/invoices/{invoiceId}/waiver")
    @PreAuthorize("hasRole('REALM_STAFF')")
    public ResponseEntity<Void> waiveInvoice(@PathVariable UUID invoiceId, @Valid @RequestBody WaiverRequestDto request,
                                              @AuthenticationPrincipal Jwt jwt) {
        billingApi.waiveInvoice(invoiceId, request.reason(), jwt.getSubject());
        return ResponseEntity.ok().build();
    }

    /**
     * Mirrors PolicyController.getPolicy's exact structure: realm-membership check via
     * Authentication.getAuthorities(), then jwt.getClaimAsString("party_id") vs the resource's
     * own owning party id, then a real AccessDeniedException (403) on mismatch -- fail-closed
     * on a null claim, not fail-open. Read PolicyController.java's own implementation of this
     * exact method before writing this copy, and match it precisely rather than approximating.
     */
    private void enforceCustomerOwnPolicyOnly(PolicyView policy, Jwt jwt, Authentication authentication) {
        boolean isCustomer = authentication.getAuthorities().stream()
            .map(GrantedAuthority::getAuthority).anyMatch("ROLE_REALM_CUSTOMERS"::equals);
        if (!isCustomer) {
            return;
        }
        String ownPartyId = jwt.getClaimAsString("party_id");
        if (ownPartyId == null || !ownPartyId.equals(policy.policyholderPartyId().toString())) {
            throw new AccessDeniedException("Customer does not own this policy");
        }
    }
}
```

## Self-Review Notes

**1. Automatic-issuance premium calculation is a new, real financial computation this plan adds to `policy`, not something any design doc specified.** `TZ_BASE_PREMIUM_RATE_PER_MILLE` and the `annualPremium = sumAssured × (rate/1000) × (1 + loading/100)` formula are this plan's own invention, following the codebase's established externalize-to-refdata convention (four prior precedents) but genuinely new in kind — every prior placeholder was a *duration* or *rate already named in a design doc* (contestability months, reinstatement window, loan interest rate); this is the first placeholder this plan itself introduces the entire shape of. Manual issuance (staff supplies the amount directly) is not a judgment call — it mirrors `sumAssured`'s own existing precedent exactly. The automatic path is the real judgment call; if a reviewer or the human partner would rather automatic issuance leave `premiumAmount` unset (`0`, rejected by the new `CHECK (premium_amount > 0)` constraint) and require a follow-up manual step, that is a materially different, smaller-scope design this plan does not build — flagging explicitly rather than silently assuming consent.

**2. The `pg_cron` + `SECURITY DEFINER` sweep function is the single largest new piece of infrastructure this plan adds, and it is genuinely novel in class, not just in content.** M3's `policyloan/V2` event trigger established the *precedent* that DB-owner-level automation may bypass RLS for non-`app_role` purposes, and it passed final review — but that trigger reacted to DDL (partition creation), a rare, administrator-triggered event. This plan's function runs unconditionally, cross-tenant, every 15 minutes, forever, touching business data (invoice/arrears/receipt status) directly. The blast radius of a bug in this function is larger than the partition-mirroring trigger's, precisely because it runs so much more often against so much more data. This plan's own Task 5 Step 1 already mandates empirical verification against the real image before trusting the SQL — but the **design choice itself** (state-transition-via-cron rather than, say, building a minimal tenant-directory table and a genuinely `@Scheduled` per-tenant loop) was made by this plan's own reasoning, not handed down by any design doc, and deserves the human partner's explicit sign-off before Task 5 is dispatched, not just after Task 5's SQL is empirically verified to work.

**3. The dunning-escalation day thresholds (7/14/21/30 days) are this plan's own placeholder guess, seeded nowhere in any design doc.** `docs/03-aggregate-design.md` names the 5 levels and their actions but specifies no timing at all — these numbers exist so the system is testable and complete, not because they reflect any real collections policy. Marked `PLACEHOLDER` in the migration per convention, but worth restating here since it's easy to miss amid the SQL: a real insurer's actual dunning cadence could be dramatically different, and nothing about this plan's code would need to change to update it — only the `refdata` values — which is the entire point of externalizing it, but the values themselves carry zero authority.

**4. `GracePeriodTriggered`/`GracePeriodExpiring` may ship unimplemented.** Task 4 Step 1 explicitly permits collapsing these into `PremiumOverdue`+`PolicyLapseRecommended` if time is short, with a mandate to report the gap rather than hide it — but this means the design doc's stated 8-event `billing` producer list (`docs/05-event-catalog.md:25`) may ship as 6 events, not 8, depending on how Task 4 actually goes. Flag for the final review to confirm which happened and rule on whether it blocks merge.

**5. `captureFieldReceipt`'s idempotency-race gap (Task 5 Step 2's own inline comment) is a known, accepted gap, not silently introduced.** The check-then-insert pattern has a real TOCTOU window under genuine concurrent duplicate submission; the DB's composite unique index is the actual backstop, but this method doesn't currently catch the resulting `DataIntegrityViolationException` and translate it to a clean idempotent-replay response — it would surface as a raw 500. Flagged in-line for Task 5 to close if time permits, and flagged again here so the final review checks whether it was actually closed or deliberately deferred with a stated reason (matching this project's now-standard practice, rather than an unnoticed gap).

**6. `PolicyEndorsed` consumption is a real listener wired to a real no-op** (Task 3 Step 4's `handlePolicyEndorsed` calls `regenerateScheduleForEndorsement` with `null` productVersionId/effectiveDate, and that method's own body does nothing when no premium-changing endorsement type exists). This is correct given M3's actual `EndorsementInput` shape, but is exactly the kind of "wired but inert" pattern M3's own ledger flagged for `LoanDisbursementRequested`/`LoanSettledForPayout` — restating it here so it isn't mistaken for a bug when the final review encounters it.
